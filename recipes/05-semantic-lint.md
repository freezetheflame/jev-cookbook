# 语义规则检查

状态：源码核查 + 离线检查。核查日期：2026-10-11。

## 适用场景

用自然语言描述局部业务规则，检查 PR 的新增变更，例如写日志时是否泄露客户地址。

## 请求

[完整 JSON](../examples/semantic-lint.json) 放文件名与 diff，一个 Noul 判断是否违反给定规则。问题区分新增、删除、未变上下文，仅判断当前变更。

## 判断与选项

规则写可观察的违规形式，用代码按文件路径匹配适用规则。只将当前 hunk 与适用规则的组合提交，避免无意义的全仓库全规则组合。

softlint 上游在判违规后，用新的 Choice 从真实新增行 ID 中选择位置。第二阶段需要第一阶段输出，不能假定同批独立问题能互相传结果。

## 结果处理

softlint 默认违规概率 ≥ 0.8 才进入位置选择。其默认值是作者设定，本仓库未评估。代码将候选 ID 映射回真实 diff 行，越界或缺失输出进入 review。

服务失败应在检查状态中展示为失败/未评估，不能作为“没有违规”。

## 验证与局限

测误报、漏报与位置精度。局部 diff 可能缺少跨文件权限检查、调用链或删除逻辑；语义检查不能自动替代完整代码审查。代码或注释中的指令文本也需加入对抗样本。
